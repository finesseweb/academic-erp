# ADR 149 — System Reservation Category is not manually mapped at Application Entry

**Date:** 2026-09-09  
**Status:** IMPLEMENTED — QA REQUIRED

## Context
The Admission Form designer already supports a system-purpose field named `CANDIDATE_RESERVATION_CATEGORY`. That field is backed by the University Reservation Category Master and its options are generated by the ERP. The College `Map Form for Application Entry` dialog was nevertheless also asking the operator to choose a `Candidate Reservation Category Field`, creating a second configuration point for the same system concept.

This duplication was confusing and could allow an arbitrary SELECT/RADIO field to be treated as the candidate's reservation category even though the form already has an authoritative system field.

## Decision
1. `CANDIDATE_RESERVATION_CATEGORY` is the authoritative Admission Form system field for the candidate's own reservation category.
2. College Form-to-Offering mapping no longer exposes a manual Candidate Reservation Category field selector.
3. When a form is mapped to a College Program Offering + Admission Cycle, the backend automatically discovers the ACTIVE system-purpose reservation field from the effective template/parent template and stores its field id only for backward compatibility with the existing mapping schema.
4. Seat Allocation resolves the candidate category from the submitted value belonging to the system-purpose field first.
5. Existing historical mappings remain supported only as a legacy fallback. New mappings do not allow arbitrary field selection.
6. Seat Allocation distinguishes source as `SYSTEM_FORM_FIELD`, `LEGACY_FORM_MAPPING`, or `MANUAL` for audit clarity.
7. If the Admission Form does not contain the system Reservation Category field, Seat Allocation requires authorized manual category confirmation. This does not make the physical reserved-seat bucket and the candidate's own reservation category the same concept.
8. Reservation category remains separate from physical seat-category consumption. Open/unreserved seats and reserved seat buckets continue to follow Seat Allocation rules.

## UI
`Map Form for Application Entry` keeps Program Offering, Admission Cycle and `Require Seat / Category Selection?` controls. The previous Candidate Reservation Category field dropdown is replaced with read-only guidance that the system field is consumed automatically.

## Compatibility
The existing `reservation_category_field_id` database column is retained so older data and historical mappings remain readable. No database migration is required.

## QA
- Map an ACTIVE form containing the system Candidate Reservation Category field; no manual category-field selector should appear.
- Submit an application selecting ST/SC/OBC/etc. from the master-backed system field.
- Seat Allocation should auto-fill and lock the candidate category from the system field.
- Verify a legacy mapping still resolves through the backward-compatible fallback.
- Verify a form without the system field requires manual candidate-category confirmation at Seat Allocation.
