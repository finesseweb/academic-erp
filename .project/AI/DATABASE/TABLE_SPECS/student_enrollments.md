# Table: `student_enrollments`

## Purpose
Authoritative academic membership of a Student in one College Program Offering. Separates permanent Student identity from session/programme placement.

## Columns
- `student_id`, `college_id`, `college_program_offering_id` — required ownership/membership chain.
- `admission_id` — nullable unique Admission provenance for Admission-originated enrollment.
- `batch_id`, `section_id` — nullable operational placement.
- `source_type` — `ADMISSION|IMPORT`.
- `status` — `ENROLLED|CANCELLED`.
- `enrolled_at`, `enrolled_by`.
- `cancelled_at`, `cancelled_by`, `cancellation_reason`.
- timestamps.

## Constraints
- Unique (`student_id`, `college_program_offering_id`).
- `admission_id` unique when present.
- Batch/Section must later be validated against the same offering hierarchy by ENR-2/assignment workflows; FK existence alone is not sufficient business validation.

## ENR-2 write behavior
A successful canonical enrollment creates one `ENROLLED` row for the confirmed Admission and resolved College Programme Offering with `source_type=ADMISSION`, `enrolled_at`, and actor. Existing unique constraints remain the database backstop against duplicate Admission/offering enrollment.

## ENR-3 / ADR 203
- `class_roll_no` — nullable until identity assignment; Enrollment-owned and unique within `college_program_offering_id` when present.
- Exam Roll is intentionally not stored/generated by ENR-3.

## ENR-3.3 addition
- `class_roll_scope_key` varchar(120), nullable: immutable scope snapshot used when a Class Roll is assigned (for example `OFFERING:1` or `OFFERING:1|DISCIPLINE:5`).
- Unique identity rule is `(college_id, class_roll_scope_key, class_roll_no)` so the same Class Roll may legitimately exist in separate Discipline scopes while duplicates inside the same scope are rejected.
- Existing assigned Class Rolls are migrated to their historical Programme Offering scope without renumbering.
